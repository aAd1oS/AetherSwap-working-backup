# AetherSwap 账号配置与初次交易

本文件合并原“账号选择与安全问答”和“初次交易建议步骤”，适用于账号已经过基本交易限制、准备进行第一次小额真实闭环的情况。

## 1. 先理解资金流

当前默认闭环是：

```text
人民币或支付账户
  -> 在 BUFF 购买饰品
  -> 饰品通过 Steam 报价进入库存
  -> 等待 Steam 交易冷却
  -> 上架 Steam 社区市场
  -> 成交后得到 Steam 钱包余额
```

Steam 钱包余额可以购买游戏、DLC、软件和社区市场物品，但通常不能通过 Steam 官方直接提现。

如果把饰品卖到第三方平台，可能获得可提现余额，但当前 AetherSwap 的自动出售逻辑主要面向 Steam 社区市场。更换购买平台或自动出售平台需要单独开发和风控审计，不能只改一个网址。

## 2. 账号选择和风险

### 新账号

优点：与常用大号隔离，凭证泄露、错误交易或平台限制的影响范围较小。

缺点：可能有 Steam Guard、市场、好友、充值和交易冷却限制。账号必须通过正常使用和官方规则解除限制，不要尝试换区、换 IP 或绕过等待时间。

### 常用大号

即使是多年老号、没有频繁交易记录，风险也不是零：

- Cookie、Steam Guard 密钥或邮箱授权码泄露会直接影响主账号。
- 自动上架参数错误可能处理不该出售的物品。
- 第三方平台风控可能限制账号或市场访问。
- 网络出口频繁变化可能触发额外验证。

程序已经有“只出售本地购买记录对应库存”的保护，但不能代替账号隔离、备份和小额验证。

## 3. 必须保护的凭证

以下内容相当于登录或交易权限，不得截图、发群、写入 Markdown 或上传 GitHub：

- Steam 密码。
- Steam Cookie，尤其是 `steamLoginSecure`、`sessionid` 等字段。
- BUFF Cookie 和 `session`。
- `shared_secret`。
- `identity_secret`。
- Steam `.maFile`。
- 邮箱 IMAP 授权码。
- PushPlus Token。
- 代理账号和密码。

`shared_secret`用于生成 Steam Guard 动态验证码；`identity_secret`用于确认交易或上架。两者都不是普通配置值。

## 4. Steam Guard 配置

页面中快速变化的一组验证码就是 Steam 令牌功能。它通常每约 30 秒更新一次。

配置步骤：

1. 打开“系统设置”或引导页。
2. 填写 `shared_secret`。
3. 保存后进入“Steam 令牌”。
4. 确认能生成验证码。
5. 如需自动确认上架，再填写 `identity_secret` 和设备信息。

不要把整个 `.maFile`放进 `docs`。只通过本地配置界面保存项目需要的字段。

## 5. Steam 账号与 Cookie

### 多账号切换

当前版本已按账号分别保存Steam Cookie、`session_id`、SteamID、`shared_secret`、`identity_secret`和`device_id`，购买、订单和出售记录也按账号隔离。

切换步骤：

1. 先停止购买任务并处理完页面上的待支付确认。
2. 打开“账号管理”，选择目标账号并点击“设为当前”。
3. 页面重新载入后，检查账号详情中的Cookie、令牌和身份一致性状态。
4. 打开设置页，确认“Steam令牌”上方显示的是目标账号。
5. 目标账号首次使用时，重新登录Steam并保存自己的Cookie。
6. 为目标账号单独填写令牌密钥，不要复制另一账号的密钥。
7. 验证账号成功后，再刷新库存和启动任务。

任务运行或存在待支付确认时，程序会拒绝切换账号。新账号没有配置时保持为空，不会继承旧账号Cookie或令牌。

2026-08-10迁移时发现旧全局Cookie属于另一个已保存账号，因此当前小号首次启动新版本后需要重新登录一次；已有购入和订单记录不会丢失。

### 推荐登录方式

1. 打开“账号管理”。
2. 添加 Steam 用户名、Steam ID 等必要信息。
3. 确认该账号已设为当前账号，点击账号详情中的“更新 Steam 信息”。
4. 在打开的浏览器里完成 Steam 登录和 Steam Guard。
5. 返回项目保存 Cookie。
6. 点击一次“验证账号”。

“更新 Steam 信息”负责打开项目浏览器并更新 Cookie；“验证”只检查已经保存的信息。验证出现 HTTP 302 或“暂时无法验证”时不会自动弹出浏览器，需要主动点击“更新 Steam 信息”。浏览器能打开 Steam 页面，不等于项目 Cookie 一定有效；项目验证有效，也不代表市场接口没有临时限流。

### 手动 Cookie

只有自动浏览器无法使用时才采用手动方式：

1. 在本机 Chrome 或 Edge 登录 Steam。
2. 打开开发者工具的 Application/应用标签。
3. 在 Cookies 中选择 `steamcommunity.com` 和相关 Steam 域名。
4. 按项目输入框要求拼接 Cookie。
5. 保存后只验证一次。

不要把 Cookie 发到聊天、文档或 GitHub。Cookie 过期后重新获取，不要反复用旧 Cookie 验证。

## 6. BUFF 账号与 Cookie

1. 在浏览器或 BUFF App 中正常登录。
2. 完成 Steam 绑定、手机号和平台要求的验证。
3. 使用项目浏览器登录，或手动保存 BUFF Cookie。
4. 确认能读取商品或订单信息。

常见状态：

- `未携带 session`：Cookie 不完整或已经失效。
- `Action Forbidden`：账号、IP 或接口访问受到平台限制。
- 页面要求人机验证：先停止任务，在正常浏览器完成验证。

被限制时不要高频重试，也不要批量切换代理绕过平台限制。

## 7. PushPlus 配置

当前项目引导将 PushPlus Token 视为必填项，用于待付款、人工介入和后台异常通知。

配置步骤：

1. 登录 PushPlus。
2. 创建或获取 Token。
3. 确认接收渠道已经绑定并允许接收消息。
4. 在 AetherSwap“系统设置”填写 Token。
5. 保存配置。

Token 只保存在本地配置中。不要写进本文件，也不要提交到 GitHub。

即使配置了通知，付款前仍要在面板核对商品、数量和金额；推送不能代替交易确认。

## 8. 邮箱 IMAP

邮箱功能是可选的，用于识别付款结果邮件或辅助自动确认流程。

不配置邮箱时，可以在面板手动点击付款成功或失败。第一次交易建议先使用手动确认，确认整条流程稳定后再决定是否增加邮箱自动化。

若启用邮箱：

- 使用邮箱提供的 IMAP 授权码，不要使用邮箱登录密码。
- 限制允许的发件人和主题。
- 单独使用一个低权限邮箱更安全。

## 9. 第一次交易前检查

### 账号

- [ ] Steam Guard 已启用并完成必要等待期。
- [ ] Steam 社区市场可正常打开。
- [ ] BUFF 已绑定正确的 Steam 账号。
- [ ] Steam 和 BUFF Cookie 都来自同一套目标账号。
- [ ] PushPlus 已配置。

### 程序

- [ ] 订单台账没有待支付或待核对订单。
- [ ] 今日投入额度是你能接受全部损失的金额。
- [ ] 当前买入策略是保守策略。
- [ ] 自动出售策略已经理解；不确定时先关闭自动出售。
- [ ] 日志没有持续网络错误。

### 金额

第一次只验证闭环，不追求利润。建议选择即使全部损失也不影响生活的小额资金。

不要因为程序已经连续买入成功，就马上把金额扩大十倍。至少完成一次“购买、入库、冷却、上架、成交”的完整周期后再调整。

## 10. 今日投入额度

当前 `target_balance`被解释为当天自动任务的投入上限：

- 今日已确认自动购买会计入额度。
- 程序重启后不会清零。
- 手动添加到操作记录的购买不占自动额度。
- 待支付或付款待核对订单会先占用额度。
- 到本地日期的第二天自动开始新的当日额度。

例如今日额度为 20 元，已经确认购买 8 元，还有一个 5 元待核对订单，则剩余额度为 7 元。

## 11. 第一次购买

1. 启动桌面版。
2. 打开“操作记录”，查看订单台账和今日额度。
3. 点击“同步入库状态”。
4. 点击“刷新商品现价”。
5. 回到仪表盘启动任务。
6. 观察 SteamDT、BUFF 和 Steam 预检日志。
7. 收到 PushPlus 待付款通知后回到面板。
8. 核对商品名、单价、数量和总价。
9. 完成付款。
10. 点击“已完成支付”。
11. 等待订单状态进入待发货或待接收报价。

不要在第一笔还未确定状态时再次启动任务。

## 12. 未决订单处理

项目会在展示付款入口前保存平台订单号。以下状态会阻止继续锁单：

- 待支付。
- 用户已确认付款。
- 付款待核对。
- 需要人工处理。

程序重启后这些状态仍然存在。

处理顺序：

1. 打开 BUFF 的购买/订单页面。
2. 按平台订单号核对实际状态。
3. 已付款就等待发货，不要解除阻断后重复购买。
4. 只有订单确实未支付、已取消或已退款时，才在台账点击“确认已取消”。

该按钮只解除本地阻断，不能改变 BUFF 平台状态。

## 13. 入库和冷却

付款后：

1. 等待 BUFF 卖家发货。
2. 点击“同步入库状态”，或等待后台收货 worker。
3. 项目可能接受已有 Steam 交易报价。
4. 入库后记录 `assetid`、入库时间和交易冷却时间。
5. 点击“刷新库存”确认物品确实存在。

Steam 的交易冷却和可上架状态以 Steam 实际显示为准。不要通过改系统时间或换 IP 尝试绕过。

## 14. 第一次上架

上架前检查：

- 商品已经入库。
- 交易冷却已经结束。
- 当前市场价已刷新。
- 上架价格和策略计算结果合理。
- 该商品确实属于 AetherSwap 的本地购买记录。

建议第一次先使用人工确认或保守出售策略。上架后查看 Steam 市场的在售记录和 Steam Guard 确认状态。

## 15. 出售策略概念

具体策略会随代码版本变化，但可以用以下方式理解：

- 跟随市场底价：成交较快，可能压低收益。
- 价格墙/卖单深度定价：参考多个卖单档位，减少被异常低价带偏。
- 趋势等待：价格走势不利时暂不上架。
- 利润或折扣保护：当前出售比例差于购买时预期时跳过。
- 同名在售数量保护：避免同一商品一次上架过多。

不理解某个参数时，不要同时修改买入和卖出策略。一次只改一项，并保留修改前数值。

## 16. 完成闭环后的复盘

检查：

- 实际购买总额。
- 购买时 Steam 市场价。
- 冷却期间价格变化。
- 实际上架价和成交价。
- Steam 手续费后的余额。
- 实际余额转化比例。
- 期间出现的网络、风控和人工操作。

只有在记录完整、没有重复订单、能解释每个状态变化时，才考虑增加投入。

## 17. 立即停止的情况

- 商品、数量或价格与面板显示不一致。
- BUFF 或 Steam 提示账号受限、安全警告或异常登录。
- 待支付订单状态不清楚。
- Cookie、Token 或 Steam Guard 密钥疑似泄露。
- 日志连续出现 `429`、`10054`、证书错误或大量超时。
- 自动上架涉及不属于本项目购买记录的个人库存。

先停止任务、保存日志、在平台页面核对，再决定是否继续。
