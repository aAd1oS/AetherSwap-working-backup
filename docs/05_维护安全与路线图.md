## 2. 已落实的关键保护

- 手动支付明确区分“用户已确认”和“平台已确认”；只有 BUFF 平台终态才能继续创建购买记录或核销。
- 支付和购买副作用按幂等边界收口，不因重试重复下单。
- 卖出建议定期复核，但仅在建议或目标价变化时通知。
- 库存以 asset id 等稳定标识区分；批量无条件接受报价的危险入口被禁用。
- BUFF 报价与本地购买记录要求整轮全局唯一占用；部分、重复或歧义匹配失败关闭并转人工处理。
- 长时间未解决状态会触发告警；C5 只读比价不会自动产生交易副作用。
- 凭据通过环境或本地配置注入，不应进入文档、日志、截图或版本控制。

历史实施证据见 [归档索引](archive/README.md)。

## 3. 数据和运行安全

### 凭据

Cookie、API key、共享密钥和通知令牌只保存在受控本地环境。泄露后立即撤销或轮换；仅从 Git 历史删除并不能使凭据失效。

### 数据库和日志

备份前停止写入或使用应用提供的一致性方式。恢复时先复制备份并验证格式，再在隔离环境启动。日志保留订单标识和状态即可，不记录完整凭据、支付链接或敏感请求头。

### 服务暴露

本次推荐启动命令和 Windows 启动器只监听回环地址。但原始 server 模式默认可能绑定 0.0.0.0，Docker Compose 也默认向宿主发布端口，不能误认为所有启动方式均只限本机。若必须远程访问，应先补齐身份认证、授权、CSRF、防重放、限流和 TLS；本次不将远程部署作为已验收路径。

### 变更完成标准

一次维护只有同时满足以下条件才算完成：

1. 代码和文档口径一致。
2. 相关测试及全量测试通过。
3. 重复执行不会产生额外副作用。
4. 失败、未知和限流状态均能安全停止。
5. 涉及真实平台的结论明确区分“已验证”和“待样本验证”。
6. 修改原因、影响文件、验证结果和剩余风险有留档。

## 4. 当前主要问题与路线顺序

### 第一优先级：安全暴露面

- 非回环监听尚缺完整应用层认证、授权、CSRF、防重放和限流闭环。
- 单实例或租约保护仍需明确，避免两个进程同时操作同一账户和数据库。

### 第二优先级：真实交易终态

代码闭环已于 2026-08-31 完成，剩余工作只允许写成“待真实平台样本验证”：

- 手动支付已增加 `user_confirmed` 与 `platform_confirmed` 两级状态，并可从订单台账发起只读平台复核。
- BUFF 报价匹配已要求完整一一对应，且同一轮每条购买记录只能被一个报价占用；歧义记录进入人工处理。
- Steam 历史已分页读取，并显式保存展示金额、展示币种、卖家到账人民币、估算含费卖价和计算基准；币种或汇率不明时整次同步失败关闭。
- 现有订单台账已兼作统一待人工处理入口，只按当前状态展示允许的取消、换单或平台复核操作。
- BUFF 真实购买字段、报价、到账，以及 Steam 分页、币种和手续费语义仍需按第 5 节做受控样本验证。

### 第三优先级：策略契约与流动性

代码闭环已于 2026-09-01 完成，后续只做真实样本校准和按证据调整阈值：

- 设置新增“上架分段自动模式策略”开关，默认关闭并保持原 24 小时复评；开启后按 24h/48h/72h 分段使用 72/48/24 小时预计等待门槛。
- 分段模式缺少可靠成交量时禁止自动降价，也不会自动上调滞销挂单；下架、asset id 唯一同步和重新交回当前出售策略继续复用原安全状态机。
- 数学模块已补齐拆分运行时输出；非数学筛选、金额、仓位、流动性、卖压、趋势、价格位置和出售保护继续按已启用模块实际执行。
- 设置新增模块判定日志开关，默认关闭；开启只增加可解释输出，不改变策略启停或安全边界。
- 卖压模块启用但日销量或卖单深度缺失时失败关闭，避免把“不可计算”误当作通过。

路线原则是先封闭资金与权限风险，再补真实平台终态，最后优化收益和自动化。不得因为策略收益更显眼而调换顺序。

## 7. 2026-08-31 第二批实施留档

### 修改原因

原流程把用户点击“已付款”与 BUFF 平台确认混为一谈；报价匹配只在单个报价内防重；Steam 售出历史只读取第一页且金额含义隐含在固定乘数中；订单台账也会对所有阻断状态显示相同操作。这些问题会造成状态提前、重复接收、漏记售出或误操作。

### 影响范围

- 付款和订单状态：`app/pipeline_steps.py`、`app/order_state.py`、`app/database.py`。
- 报价唯一匹配：`app/receive_flow.py`。
- Steam 历史：`app/steam_history.py`，并由 `app/steam_listings.py` 保持原调用入口兼容。
- 人工处理入口：`app/routes/transactions.py`、`web/index.html`、`web/js/transactions.js`。
- 回归测试：付款状态、订单聚合、asset id/付款原子性、报价唯一性、Steam 历史分页与币种、订单台账操作权限。

### 验证结果

- 第二批定向回归：40 项通过。
- 项目完整离线回归：456 项通过（31.42 秒）。
- 本次没有发起真实付款、购买、接受报价、上架、下架或平台确认操作。

### 剩余风险

离线测试不能证明 BUFF 与 Steam 当前线上字段、分页上限、钱包币种编号、手续费展示和状态文案没有变化。真实验证必须继续遵守第 5 节的最小金额、单账户、单订单和可人工停止约束；任何字段未知、币种无汇率或分页不前进都会失败关闭，不应为了跑通而恢复猜测逻辑。

## 8. 2026-09-01 第三批实施留档

### 修改原因

原滞销处理已有 24 小时复评、下架、新 asset id 同步和重挂能力，但没有显式区分 24h、48h、72h；缺少成交量时旧等待门槛仍可能允许降价。数学模块的拆分定义与样例已经存在，但部分真实运行时输出没有按拆分模块暴露，声明式模块日志也无法在设置中关闭。

### 影响范围

- 分段决策与出售复评：`app/sell_pipeline.py`、`app/services/workers.py`。
- 配置与设置页：`app/config_schema.py`、`web/index.html`、`web/js/settings.js`。
- 数学/非数学模块输出和日志：`app/strategy_engine.py`、`app/pipeline_steps.py`。
- 回归测试：配置布尔归一化、设置绑定、24h/48h/72h 门槛、成交量缺失失败关闭、禁止自动上调、模块日志开关和拆分数学输出。

### 验证结果

- 定向策略与设置回归：77 项通过。
- 项目完整离线回归：462 项通过（25.17 秒）。
- 同步修正一个已落后于页面 `transactions.js?v=5` 的静态资源版本断言。
- 本次没有发起真实购买、付款、报价接受、上架、下架、改价或确认操作。

### 剩余风险

预计等待时间依赖 Steam 历史成交量和当前可见卖单深度，线上数据仍可能限流、缺失或与真实排队速度不同。分段模式默认关闭；首次真实验证应只对单账户、少量低价受管挂单开启，核对 24h/48h/72h 日志、目标价、下架结果和新 asset id 后再扩大范围。

## 9. 2026-09-01 购入历史异常值清洗实施留档

### 修改原因

原有 IQR 只清洗总体均价、CV 和部分价格分位；每日价格序列、EMA、斜率和 R² 仍使用原始记录，单个错误高低价可能改变趋势判断。直接删除所有异常点又可能把真实的连续行情变化误当成脏数据。

### 影响范围

- 核心计算与包装：`analysis/stability.py`、`app/services/analysis_client.py`。
- 配置与策略模块：`app/config_schema.py`、`app/strategy_engine.py`。
- 购入接线和模块日志：`app/pipeline_steps.py`。
- 回归测试：`tests/test_strategy_shadow_and_wait.py`、`tests/test_strategies.py`、`tests/test_pipeline_steps.py`、`tests/test_config_schema.py`。

### 已落实行为

- 复用现有 IQR，不增加第三方统计依赖；按同一索引同步保留时间、价格和成交量。
- 允许清洗的孤立点从均价、VWAP、CV、日均、EMA、趋势拟合和分位计算中一致移除。
- 最近连续三天同向越界视为可能换挡，异常占比超过上限视为数据不可靠；两种情况都不删除数据并失败关闭。
- 系统默认购入策略加入可调模块；未包含新模块的既有策略保持旧行为。
- 当前保存的两个系统默认策略副本已显式加入该模块并启用默认参数；其他未迁移策略仍保持旧行为。
- 审计输出和拒绝日志遵守现有“策略模块判定日志”开关。

### 验证结果

- 定向策略、配置和异常数据回归：81 项通过。
- 项目完整离线回归：468 项通过（25.74 秒）。
- 本次没有发起真实购买、付款、报价接受、上架、下架、改价或确认操作。

### 剩余风险

IQR 能识别统计离群点，不能证明 Steam 历史记录本身完整，也不能预测真实市场换挡。默认的 `1.5` 倍 IQR、`20%` 异常占比和连续三天保护需要结合脱敏真实样本观察；调参时应先开启模块判定日志、小规模运行，不应为了提高候选通过率关闭持续行情保护。
