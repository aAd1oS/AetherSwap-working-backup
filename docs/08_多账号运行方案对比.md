# AetherSwap 多账号运行方案对比

- 记录日期：2026-08-09
- 更新日期：2026-08-12
- 当前状态：方案A已实施；方案B保留为备选设计
- 目标：在不混用 Steam 身份、交易记录和令牌的前提下，让小号与大号都能使用 AetherSwap
- 共同原则：同一时间只允许一个 Steam 账号运行真实交易任务

## 1. 背景与当前限制

改造前的账号管理可以保存多个账号并选择当前账号，但不是完整的交易身份切换：

- 账号列表中的用户名、密码、SteamID 和登录浏览器目录可以按账号区分。
- Steam Cookie、`session_id` 和运行时 `steam_id` 仍使用一套全局凭据。
- `shared_secret`、`identity_secret` 和 `device_id` 仍属于全局设置。
- 购买、订单和出售记录没有账号归属字段。

上述限制已由方案A处理。方案B继续保留，供以后需要进程级隔离时参考。

## 2. 方案 A：应用内部完整账号切换

### 2.1 核心思路

继续使用同一个 AetherSwap 实例和现有 `config/app.db`，增加账号级凭据表及交易归属字段。现有购买、收货、库存和出售逻辑尽量不重写，而是统一从“当前账号上下文”读取身份。

### 2.2 已完成内容

1. 新增账号级凭据，分别保存每个账号的 Cookie、`session_id`、SteamID、用户名、密码、`shared_secret`、`identity_secret`、`device_id`、地区和币种。
2. 为购买记录、BUFF订单和出售记录增加 `account_id`，所有查询和写入均按账号过滤。
3. 将现有 `get_steam_credentials()` 改为兼容旧调用、默认读取当前账号的统一入口。
4. 任务运行和待支付确认期间禁止切换账号，交易函数继续复用原入口。
5. 切换前停止任务并等待当前请求结束；切换后清理旧账号的网络会话、库存缓存和验证状态。
6. 设置页显示“当前配置账号”，并随账号切换展示对应令牌，禁止复用其他账号的密钥。
7. 下单前核对当前账号SteamID、Cookie所属SteamID和BUFF收货SteamID；不一致时禁止锁单。
8. 自动迁移现有小号交易记录；旧全局Cookie按其真实SteamID归入匹配账号，不按当前页面选择盲目迁移。
9. 自动出售增加账号级独立开关；没有本地购入记录的新账号默认关闭，已有受管购入记录的账号在迁移时保留原行为。
10. 自动出售只接受当前账号购买记录中完全一致的 `assetid`，不再按同名饰品兜底；库存界面分别显示“自动托管”和“个人保护”。
11. 库存归属支持账号级手动覆盖为“个人保护”或“自动托管”，也可恢复“自动判断”；覆盖按`account_id + assetid`保存，任务运行时禁止修改。

### 2.3 2026-08-10迁移结果

- 现有14条购入记录和7条BUFF订单全部归入当前小号。
- 未发现未归属购买、订单或出售记录。
- 旧全局Cookie所属SteamID与当前小号不同，已归入实际匹配的另一个账号。
- 当前小号保留原令牌配置，但Cookie留空；下次使用时必须重新登录当前小号一次。
- 新账号没有自己的Cookie和令牌时返回空配置，不会继承其他账号。
- 购买、收货和出售前增加身份保护；账号SteamID与Cookie所属SteamID不一致时停止操作。
- 设置页显示令牌当前所属账号，账号详情显示Cookie、令牌、身份一致性及本地记录数量。
- 2026-08-12个人库存保护和手动归属补充完成后，完整离线回归结果为`285 passed`；Python和前端JavaScript语法检查通过。
- 测试套件统一使用临时数据库，直接运行`pytest`不会修改真实`config/app.db`。
- 当前小号Cookie为空是迁移后的预期保护状态；重新登录当前小号前，身份保护会阻止购买、收货和出售。

### 2.4 优点

- 一个界面即可管理多个账号，日常操作最方便。
- 可以查看单账号数据，也可以汇总全部账号的投入、库存和收益。
- Cookie、令牌、库存和交易记录具有明确归属。
- 后续扩展账号状态检查、快速切换和分账号策略更自然。
- 不需要维护两套程序和两个服务地址。

### 2.5 缺点

- 改动面较大，会涉及数据库、认证、购买、收货、出售、后台任务和前端。
- 数据迁移和后台任务竞争需要谨慎处理。
- 一个实例发生严重故障时，可能同时影响所有账号。
- 测试量较大，必须证明两个账号之间不会交叉读取或写入数据。

### 2.6 实际实施方式

实际采用兼容层实现，没有替换购买、收货和出售主流程。账号级凭据与交易过滤集中在数据库和配置入口，原调用方继续使用 `get_steam_credentials()`、`get_purchases()` 等既有函数。

## 3. 方案 B：Windows 与 Docker 双实例隔离

### 3.1 核心思路

运行两个相互独立的 AetherSwap 实例：一个运行在 Windows，另一个运行在 Docker。两边使用相同且固定的代码版本，但数据库、配置、Cookie、令牌、日志和浏览器资料完全分开。

示例：

```text
Windows实例：账号A，http://127.0.0.1:28472
Docker实例：账号B，http://127.0.0.1:28473
```

### 3.2 必要改进

1. 增加 `AETHERSWAP_DATA_DIR`，让Docker固定使用独立的 `/data`，不得挂载Windows实例正在使用的 `config/`。
2. 每个实例设置名称和预期SteamID，启动任务前核对Cookie及BUFF收货SteamID。
3. Docker端口只绑定 `127.0.0.1`；服务器模式增加管理密码或随机访问令牌。
4. 增加数据目录占用检测，阻止两个实例同时打开同一个数据库。
5. 增加跨实例运行锁，确保一次只有一个实例能够执行真实交易任务。
6. 固定Docker镜像与Python Playwright版本，并在构建后测试浏览器能否启动。
7. 分别提供Docker数据备份、恢复、日志导出和实例状态展示。

### 3.3 可选的 Windows 登录辅助 App

Docker处于无桌面模式，不能直接弹出Windows登录浏览器。可以增加一个仅在本机运行的登录助手：

1. Docker页面生成短时一次性配对码。
2. 用户运行Windows登录助手，由它打开Playwright浏览器。
3. 用户正常完成Steam登录。
4. 助手过滤出必要Cookie，并发送到 `127.0.0.1` 上的Docker服务。
5. Docker核对预期SteamID后保存Cookie，配对码立即失效。

安全要求：不传Steam密码和令牌密钥、不记录Cookie、只监听本机、Docker未主动请求时拒绝接收，并在更新后显示实际账号名称和SteamID。

### 3.4 优点

- 两个账号在进程、配置和数据库层面天然隔离。
- 对现有交易代码的侵入较小，实施速度通常快于完整多账号改造。
- 一个实例损坏时，另一个实例的数据通常不受影响。
- 可以先作为过渡方案，后续再决定是否开发应用内完整切换。

### 3.5 缺点

- 需要维护两个服务、两个地址、两套备份和升级流程。
- Docker登录及Cookie更新不如Windows桌面版方便；辅助App本身也需要维护。
- Windows与Docker通常共用公网出口IP，无法隔离Steam 429或BUFF限流。
- 两套代码版本若没有固定到同一提交，容易出现功能和数据库结构不一致。
- Docker面板若错误开放到局域网，会带来凭据和真实交易接口暴露风险。

### 3.6 预计规模

基础隔离属于中等规模，通常小于完整多账号切换。数据目录、身份校验、本机端口、安全鉴权和版本锁定完成后即可使用；Windows登录助手属于第二阶段体验改进，不是基础运行的必要条件。

## 4. 两个方案对比

| 对比项 | 方案A：应用内完整切换 | 方案B：Windows与Docker双实例 |
| --- | --- | --- |
| 数据隔离 | 依靠 `account_id` 和账号级凭据 | 依靠独立进程、目录和数据库 |
| 日常使用 | 一个界面，切换最方便 | 需要访问两个地址 |
| 初次开发量 | 较大 | 中等 |
| 交易代码改动 | 较多，需要贯穿所有流程 | 较少，主要是部署和身份保护 |
| 数据迁移难度 | 较高，需要为旧记录分配账号 | 较低，可把现有数据整体归入一个实例 |
| 登录体验 | Windows桌面登录体验不变 | Docker需手动Cookie或登录辅助App |
| Cookie和令牌隔离 | 由数据库和账号上下文保证 | 由独立数据目录天然保证 |
| 交易记录汇总 | 容易实现统一汇总 | 需要额外跨实例汇总 |
| 单实例故障影响 | 可能影响全部账号 | 通常只影响一个账号 |
| 升级维护 | 只升级一套 | 两个实例必须同步升级 |
| 网络隔离 | 没有 | 默认也没有，通常共用公网IP |
| 防止同时交易 | 应用内部任务锁 | 需要跨实例运行锁 |
| 后续扩展性 | 更适合作为长期正式方案 | 更适合作为过渡或强隔离方案 |
| 对当前可运行版本影响 | 较大，需充分回归测试 | 较小，可保留Windows稳定实例 |

## 5. 推荐选择

### 当前阶段

使用已经实施的方案A。第一次切换或新增账号后，先完成该账号自己的Steam登录、令牌配置和身份检查，再启动任务；一次只运行一个账号。

### 长期阶段

方案B暂不实施。只有以后明确需要进程级隔离、独立故障域或独立部署时，再重新评估Docker双实例及Windows登录辅助App。

## 6. 两个方案共同不能解决的问题

- 不能通过数据隔离自动获得新的公网IP。
- 不能保证绕过Steam 429、BUFF风控或平台交易限制。
- 不能替代SteamID、Cookie、令牌和BUFF收货账号的一致性校验。
- 不能允许两个账号无限制并发请求。
- 不能取消真实交易前的金额限制、订单防重复和人工检查。

## 7. 方案B实施前决策点

真正开始编码前，需要再次确认：

1. 先实施方案A还是方案B。
2. 哪个账号留在Windows，哪个账号进入Docker。
3. Docker初期使用手动Cookie，还是同时开发Windows登录辅助App。
4. 是否要求两个实例完全禁止同时启动任务。
5. 是否需要统一查看两个实例的资产与收益。

方案A已经实现；本节仅适用于未来重新考虑方案B。
