# AetherSwap 价格与支付说明

本文解释操作记录中的价格字段、当前统计公式、BUFF 可用资金调查结果，以及尚未实施的支付与价格改进方案。

适用目录：`D:\Vibe Coding\steam`

最后整理：2026-08-05

> “当前逻辑”“调查确认”“建议改进”是三种不同状态。建议改进不代表功能已经上线。

## 1. 先理解两种钱

AetherSwap 的“倒余额”流程同时涉及两种价值：

- **现金成本**：在 BUFF 等购买平台实际支付的人民币。
- **Steam 钱包价值**：饰品在 Steam 社区市场售出后进入 Steam 钱包的金额。

Steam 钱包余额通常用于 Steam 内购买游戏、DLC、软件或社区市场物品，不等于可以直接提现的现金。因此，“收益”必须先说明是 Steam 自用价值，还是按一定比例估算的现金等价价值。

## 2. 价格字段逐项解释

### 2.1 购入价

在 BUFF 实际购买饰品所付的人民币单价，也是该商品的现金成本。例如支付 `7.00` 元，购入价就是 `7.00`。它不代表 Steam 市场价格。

### 2.2 购入市场价

程序在购买当时记录的 Steam 市场参考价快照。

当前项目会结合 Steam 卖单深度、价格墙等信息形成智能参考价，所以它不一定等于网页上第一条最低卖单，也不保证未来一定能按此价格成交。它主要用于记录买入时的市场水平、与现市场价比较，以及复盘当时的折扣是否合理。

### 2.3 现市场价

最近一次刷新后取得的 Steam 当前市场参考价。

它是参考值，不是成交承诺。卖单变化、流动性、接口超时、限流、缓存和实际定价都可能让最终成交结果不同。页面中的“刷新商品现价”只更新信息，不会自动上架或出售。

### 2.4 税后价格

按当前项目的简化算法估算，饰品在 Steam 市场成交后进入 Steam 钱包的金额：

```text
税后价格 = Steam 市场总价 / 1.15
```

持有中的商品使用“现市场价”计算；已售商品使用“出售价格”计算。实际手续费和到账金额应以 Steam 最终确认页面及市场历史为准。

### 2.5 实际折扣比率

表示为了获得 `1` 元估算 Steam 钱包余额，实际付出了多少人民币：

```text
实际折扣比率 = 购入价 / 税后价格
```

例如比率为 `0.7000`，可理解为预计每获得 `1.00` 元 Steam 钱包余额，现金成本约为 `0.70` 元。

其他条件相同时，比率越低越有利。但仍需同时考虑成交量、卖单深度、七天交易冷却、价格波动和数据是否完整，不能只看单一比率。

### 2.6 变现收益

将 Steam 钱包价值按“余额变现比例”折算成现金等价价值后的理论收益，不是已经到账的现金：

```text
变现收益 = 税后价格 × 余额变现比例 - 购入价
```

当前默认余额变现比例为 `0.85`。这个比例只是配置参数，不是平台保证的回收价；真正变现还可能涉及渠道、时间、价格波动和额外成本。

### 2.7 自用收益

如果 Steam 钱包余额由自己消费时的理论价差：

```text
自用收益 = 税后价格 - 购入价
```

它适合衡量“用较少现金换取较多 Steam 消费余额”的效果，但不是现金利润。

### 2.8 市场变动

```text
市场变动金额 = 现市场价 - 购入市场价
市场变动百分比 = 市场变动金额 / 购入市场价 × 100%
```

它只反映 Steam 市场参考总价从买入时到现在的变化，没有扣除手续费和现金折算损耗，不等于实际收益。

### 2.9 出售价格与价格偏离度

当前统计代码把“出售价格”当作 Steam 买家支付的市场成交总价，再除以 `1.15` 估算卖家到账。

```text
价格偏离金额 = 出售价格 - 购入市场价
价格偏离百分比 = 价格偏离金额 / 购入市场价 × 100%
```

#### 当前界面的已知口径问题

手动标记出售的输入框目前提示“填写实际到手金额”，但统计代码会对输入值再次除以 `1.15`。如果真的填写 Steam 钱包实际到账金额，手续费会被重复扣除。

在代码修正前，手动填写时应：

- 填写 **Steam 买家支付的市场成交总价/展示成交价**。
- 不要填写已经扣除手续费后的 Steam 钱包到账金额。
- 填写后用 Steam 市场历史核对统计结果。

自动同步出售记录时，项目会把取得的净到账金额换算回总价后保存，这也说明当前 `sale_price` 的设计意图是“成交总价”。

## 3. 完整计算示例

假设 BUFF 购入价为 `7.00` 元，购入时 Steam 市场价为 `11.00` 元，当前 Steam 市场价为 `11.50` 元，余额变现比例为 `0.85`：

```text
税后价格 = 11.50 / 1.15 = 10.00 元
实际折扣比率 = 7.00 / 10.00 = 0.7000
变现收益 = 10.00 × 0.85 - 7.00 = 1.50 元
自用收益 = 10.00 - 7.00 = 3.00 元
市场变动 = 11.50 - 11.00 = +0.50 元，约 +4.55%
```

这表示按当前参考价卖出后，预计得到 `10.00` 元 Steam 钱包余额；自用理论价差为 `3.00` 元；按 `85%` 折算时，理论现金等价收益为 `1.50` 元。

## 4. BUFF 可用资金调查结论

### 4.1 调查方式

本次只读取 BUFF 商品信息和购买预览结果，没有提交订单、付款或修改代码。

对已有低价商品和用户提供的测试商品读取购买预览后，BUFF 返回的动态支付方式列表中确实存在 **“BUFF可用资金”**。

### 4.2 两次调查的实际结果

第一次调查时账号的 BUFF 可用资金为 `0`，预览中的余额方式不可点击，并返回 `enough=false`、`real_enough=false`。这只能说明当时余额不足，不能据此判断余额支付永远不可用。

充值后再次进行只读调查：账号可用资金为 `7.73` 元，样例商品价格为 `2.27` 元。该笔购买预览明确返回：

- 支付方式名称为“BUFF可用资金”。
- 本次动态支付方式编号为 `80`。
- `btn_clickable=true`。
- `enough=true`、`real_enough=true`。
- 预览余额为 `7.73` 元。
- `free_password=true`。

用户随后也在 BUFF 页面手动使用可用资金成功支付。因此可以确认：**余额充足且当前订单预览允许时，BUFF 可用资金可以用于购买。**

两次预览中同一种业务含义出现过不同编号，其他说明接口还曾把编号 `80`描述成别的付款方式。这说明支付编号和跨接口文案都不能作为固定映射；必须信任当前订单购买预览中同时返回的名称、可用性和余额字段。

上述程序调查没有锁单、提交付款或扣款。页面上的手动支付由用户本人完成。

## 5. BUFF 余额支付改进方案

以下方案 **尚未实现**。

### 5.1 动态识别支付方式

BUFF 支付方式及编号可能随账号、商品、金额和平台规则变化。后续代码应以每笔订单购买预览的实时返回为准，不能把某次见到的支付编号永久写死。

只有同时满足以下条件，才可选择 BUFF 可用资金：

```text
当前购买预览中的名称 = BUFF可用资金
btn_clickable = true
enough = true
real_enough = true（字段存在时）
返回余额 >= 本笔订单金额
没有平台错误信息
```

不要硬编码 `63`、`78`、`80`等编号，也不要根据另一个接口对编号的说明来猜测支付方式。

### 5.2 余额不可用时回退人工付款

```text
读取购买预览
  -> BUFF 可用资金可点击且足够
     -> 展示订单金额和支付方式
     -> 按资金保护规则执行
  -> BUFF 可用资金不可用
     -> 保留现有人工付款入口
```

不能因余额方式不可用而反复提交订单，也不能自动试遍多个支付编号。

### 5.3 付款必须按有副作用处理

即使某个付款接口技术上使用 `GET`，也可能产生真实扣款。实现时必须：

- 同一平台订单的付款动作最多主动调用一次。
- 网络超时后不盲目重试付款。
- 先查询平台订单状态，再决定是否人工处理。
- 将“请求已发送但结果未知”记录为未决状态。
- 未决订单继续占用预算并阻止重复锁单。
- 保留单笔金额、今日额度和首次自动付款确认保护。
- `free_password=true`意味着平台可能无需再次输入支付密码即可扣除可用资金，自动化风险高于只生成手动付款入口。

### 5.4 上线前验收

1. 用模拟数据验证动态识别。
2. 验证余额不足、不可点击或平台报错时绝不付款。
3. 验证超时后不会重复提交。
4. 验证订单状态、预算占用和本地台账一致。
5. 用最低金额商品做一次人工盯守的小额测试。
6. 对照 BUFF 订单记录确认只有一笔订单和一次扣款。

在平台订单真实性核对和幂等保护完成前，不应扩大自动付款范围。

## 6. 价格模块后续改进

### P0：统一出售价格口径

- 把手动输入框改为“Steam 买家支付总价”。
- 同时展示买家支付总价、Steam 手续费和卖家到账金额。
- 数据库明确区分 `gross_sale_price`、`fee_amount` 和 `net_wallet_amount`。
- 旧记录迁移时保留原值和来源，不静默猜测。

### P1：让计算过程可查看

- 为价格列增加简短说明或悬浮提示。
- 展示数据更新时间和来源。
- 展示折扣比率、变现收益的完整代入值。
- 区分缺少现价、缓存过期和接口失败，不用 `0` 冒充真实价格。

### P1：用实际结果核对手续费

- 当前 `/ 1.15` 可继续作为购买筛选的统一估算。
- 出售后优先从 Steam 市场历史写入真实总价、手续费和到账额。
- 统计页区分“估算值”和“已核对实际值”。

### P2：区分自用和变现目标

- 自用模式重点展示折扣比率和预计 Steam 钱包价值。
- 变现模式重点展示折算比例、渠道成本、净收益和不确定性。
- 不再用同一个“收益”混合表示钱包价差和现金利润。

## 7. 日常判断顺序

1. 看购入价，确认真实现金成本。
2. 看购入市场价和现市场价，判断参考价是否明显变化。
3. 看税后价格，估算 Steam 钱包到账。
4. 看实际折扣比率，判断现金换余额是否划算。
5. 看成交量、卖单深度和冷却时间，不只看低比率。
6. 准备自用时看自用收益。
7. 准备变现时看变现收益，并记住它只是理论值。
8. 出售后以 Steam 市场历史和钱包实际到账做最终对账。
