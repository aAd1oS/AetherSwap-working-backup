# AetherSwap 价格与支付说明

本文解释操作记录中的价格字段、当前统计公式、BUFF 可用资金调查结果，以及尚未实施的支付与价格改进方案。

适用目录：`D:\Vibe Coding\steam`

最后整理：2026-08-05

> “当前逻辑”“调查确认”“建议改进”是三种不同状态。建议改进不代表功能已经上线。

## 1. 先理解两种钱

AetherSwap 的“倒余额”流程同时涉及两种价值：

- **现金成本**：在 BUFF 等购买平台实际支付的人民币。
- **Steam 钱包价值**：饰品在 Steam 社区市场售出后进入 Steam 钱包的金额。

Steam 钱包余额通常用于 Steam 内购买游戏、DLC、软件或社区市场物品，不等于可以直接提现的现金。因此，“收益”必须先说明是 Steam 自用价值，还是按一定比例估算的现金等价价值。

## 2. 价格字段逐项解释

### 2.1 购入价

在 BUFF 实际购买饰品所付的人民币单价，也是该商品的现金成本。例如支付 `7.00` 元，购入价就是 `7.00`。它不代表 Steam 市场价格。

### 2.2 购入市场价

程序在购买当时记录的 Steam 市场参考价快照。

当前项目会结合 Steam 卖单深度、价格墙等信息形成智能参考价，所以它不一定等于网页上第一条最低卖单，也不保证未来一定能按此价格成交。它主要用于记录买入时的市场水平、与现市场价比较，以及复盘当时的折扣是否合理。

### 2.3 现市场价

最近一次刷新后取得的 Steam 当前市场参考价。

它是参考值，不是成交承诺。卖单变化、流动性、接口超时、限流、缓存和实际定价都可能让最终成交结果不同。页面中的“刷新商品现价”只更新信息，不会自动上架或出售。

### 2.4 税后价格

按当前项目的简化算法估算，饰品在 Steam 市场成交后进入 Steam 钱包的金额：

```text
税后价格 = Steam 市场总价 / 1.15
```

持有中的商品使用“现市场价”计算；已售商品使用“出售价格”计算。实际手续费和到账金额应以 Steam 最终确认页面及市场历史为准。

### 2.5 实际折扣比率

表示为了获得 `1` 元估算 Steam 钱包余额，实际付出了多少人民币：

```text
实际折扣比率 = 购入价 / 税后价格
```

例如比率为 `0.7000`，可理解为预计每获得 `1.00` 元 Steam 钱包余额，现金成本约为 `0.70` 元。

其他条件相同时，比率越低越有利。但仍需同时考虑成交量、卖单深度、七天交易冷却、价格波动和数据是否完整，不能只看单一比率。

### 2.6 变现收益

将 Steam 钱包价值按“余额变现比例”折算成现金等价价值后的理论收益，不是已经到账的现金：

```text
变现收益 = 税后价格 × 余额变现比例 - 购入价
```

当前默认余额变现比例为 `0.85`。这个比例只是配置参数，不是平台保证的回收价；真正变现还可能涉及渠道、时间、价格波动和额外成本。

### 2.7 自用收益

如果 Steam 钱包余额由自己消费时的理论价差：

```text
自用收益 = 税后价格 - 购入价
```

它适合衡量“用较少现金换取较多 Steam 消费余额”的效果，但不是现金利润。

### 2.8 市场变动

```text
市场变动金额 = 现市场价 - 购入市场价
市场变动百分比 = 市场变动金额 / 购入市场价 × 100%
```

它只反映 Steam 市场参考总价从买入时到现在的变化，没有扣除手续费和现金折算损耗，不等于实际收益。

### 2.9 出售价格与价格偏离度

当前统计代码把“出售价格”当作 Steam 买家支付的市场成交总价，再除以 `1.15` 估算卖家到账。

```text
价格偏离金额 = 出售价格 - 购入市场价
价格偏离百分比 = 价格偏离金额 / 购入市场价 × 100%
```

#### 当前界面的已知口径问题

手动标记出售的输入框目前提示“填写实际到手金额”，但统计代码会对输入值再次除以 `1.15`。如果真的填写 Steam 钱包实际到账金额，手续费会被重复扣除。

在代码修正前，手动填写时应：

- 填写 **Steam 买家支付的市场成交总价/展示成交价**。
- 不要填写已经扣除手续费后的 Steam 钱包到账金额。
- 填写后用 Steam 市场历史核对统计结果。

自动同步出售记录时，项目会把取得的净到账金额换算回总价后保存，这也说明当前 `sale_price` 的设计意图是“成交总价”。

### 2.10 候选最高价与单件最高购买价

这两个字段名字接近，但作用不同：

| 字段 | 作用时机 | 能否阻止最终锁单 |
|---|---|---|
| 系统设置中的候选“最高价” | 向 SteamDT 查询、筛选候选时 | 不能保证；后续 BUFF 实际价格可能变化 |
| 策略中心的“单件最高购买价” | 刷新 BUFF 卖单后、任何锁单之前 | 能；实际最低价超限就跳过 |

系统默认购入策略的单件上限为 `50.00` 元。这个值是资金安全边界，不是推荐购买金额；第一次实盘应按自己愿意承担的单笔风险调低。程序还会在选出最终卖单后再次核对价格，避免候选价与真实锁单价之间发生变化。

## 3. 完整计算示例

假设 BUFF 购入价为 `7.00` 元，购入时 Steam 市场价为 `11.00` 元，当前 Steam 市场价为 `11.50` 元，余额变现比例为 `0.85`：

```text
税后价格 = 11.50 / 1.15 = 10.00 元
实际折扣比率 = 7.00 / 10.00 = 0.7000
变现收益 = 10.00 × 0.85 - 7.00 = 1.50 元
自用收益 = 10.00 - 7.00 = 3.00 元
市场变动 = 11.50 - 11.00 = +0.50 元，约 +4.55%
```

这表示按当前参考价卖出后，预计得到 `10.00` 元 Steam 钱包余额；自用理论价差为 `3.00` 元；按 `85%` 折算时，理论现金等价收益为 `1.50` 元。

## 4. BUFF 可用资金调查结论

### 4.1 调查方式

本次只读取 BUFF 商品信息和购买预览结果，没有提交订单、付款或修改代码。

对已有低价商品和用户提供的测试商品读取购买预览后，BUFF 返回的动态支付方式列表中确实存在 **“BUFF可用资金”**。

### 4.2 两次调查的实际结果

第一次调查时账号的 BUFF 可用资金为 `0`，预览中的余额方式不可点击，并返回 `enough=false`、`real_enough=false`。这只能说明当时余额不足，不能据此判断余额支付永远不可用。

充值后再次进行只读调查：账号可用资金为 `7.73` 元，样例商品价格为 `2.27` 元。该笔购买预览明确返回：

- 支付方式名称为“BUFF可用资金”。
- 本次动态支付方式编号为 `80`。
- `btn_clickable=true`。
- `enough=true`、`real_enough=true`。
- 预览余额为 `7.73` 元。
- `free_password=true`。

用户随后也在 BUFF 页面手动使用可用资金成功支付。因此可以确认：**余额充足且当前订单预览允许时，BUFF 可用资金可以用于购买。**

两次预览中同一种业务含义出现过不同编号，其他说明接口还曾把编号 `80`描述成别的付款方式。这说明支付编号和跨接口文案都不能作为固定映射；必须信任当前订单购买预览中同时返回的名称、可用性和余额字段。

购买预览还可能同时返回多个都叫“BUFF可用资金”的通道。旧实现只取第一个，因此可能把旧通道的 `0.00`误认为整个账号没有余额。现在会逐个检查全部同名通道，并从中选择明确可用且余额足够的通道。账号页面显示的 `7.73` 元是账户资金事实，而某一个支付通道的 `0.00`、不可点击或“不支持支付宝余额”只描述该通道和该笔订单，二者不能混为一谈。

2026-08-06 实盘再次验证了这个边界：账号最近可信余额为 `15.11`，连续两次 retry 预览仍为 `15.11`；随后某个 `2.22` 元订单只返回编号 `63`、不可点击、带“该订单不支持支付宝余额”错误的 `0.00` 通道。期间没有锁单、付款或扣款，因此这个 `0.00`不能作为账号余额。缓存逻辑现已改为拒绝这种观察，并保留 `15.11`作为最近可信值。

上述程序调查没有锁单、提交付款或扣款。页面上的手动支付由用户本人完成。

## 5. BUFF 余额支付实现

以下安全链路已在 2026-08-06 实现。代码没有替用户执行真实自动扣款；当前验证使用模拟接口响应。

### 5.1 动态识别支付方式

BUFF 支付方式及编号可能随账号、商品、金额和平台规则变化。程序以每笔订单购买预览的实时返回为准，不把某次见到的支付编号永久写死。

程序先收集当前预览中所有名称严格等于“BUFF可用资金”的通道。只有某个通道同时满足以下条件，才可选择它：

```text
当前购买预览中的名称 = BUFF可用资金
btn_clickable = true
enough = true
real_enough = true（字段存在时）
返回余额 >= 本笔订单金额
没有平台错误信息
```

不要硬编码 `63`、`78`、`80`等编号，也不要根据另一个接口对编号的说明来猜测支付方式。

若多个通道可用，程序选择可核对余额最高的那个；若全部不可用，日志逐一显示通道编号、余额和拒绝原因。它不会因为账号总余额大于订单金额就绕过平台对当前订单的限制。

即使余额小于当前商品价格，程序仍会保留购买预览中严格匹配“BUFF可用资金”通道所报告的余额，用于仪表盘展示；“本单不可用”和“账户报告了多少可用资金”是两个不同事实。这个余额只用于展示和选择付款方式，绝不会绕过 `enough`、`real_enough`或按钮可用性判断。

### 5.2 余额不足时的两种模式

```text
读取购买预览
  -> BUFF 可用资金可点击且足够
     -> 记录动态编号、余额、订单金额和免密状态
     -> 按资金保护规则执行
  -> BUFF 可用资金不可用
     -> 跳过本件，不锁单
```

系统设置提供两种处理方式：

- **BUFF 可用资金（自动扣款）**：严格模式。余额不足或订单不支持余额时跳过本件，再检查其他候选；不会锁单，也不会自动改走支付宝或微信。
- **智能：余额优先，不足转手动支付**：先比较购买预览余额和本笔价格。余额足够时走余额自动扣款；平台明确返回不足或订单不支持时，整笔改用用户选择的微信/支付宝，并进入原有人工付款流程。

智能模式不做部分余额加部分微信/支付宝的拆分付款。购买预览超时、接口报错、登录状态异常或结果不明确时，不允许自动回退，因为此时程序并不知道余额通道的真实状态。严格模式和智能模式都必须勾选独立自动扣款授权。

### 5.3 付款必须按有副作用处理

即使付款接口技术上使用 `GET`，也可能产生真实扣款。当前实现遵守：

- 同一平台订单的付款动作最多主动调用一次。
- 网络超时后不盲目重试付款。
- 获得平台订单号后先写入本地台账，再调用余额支付。
- 支付调用后只读查询一次平台订单状态，再决定成功或人工处理。
- 将“请求已发送但结果未知”记录为未决状态。
- 未决订单继续占用预算并阻止重复锁单。
- 保留单笔金额、今日额度和独立自动付款授权保护。
- `free_password=true`意味着平台可能无需再次输入支付密码即可扣除可用资金，自动化风险高于只生成手动付款入口。

### 5.4 余额展示与手动刷新

仪表盘展示最近一次可信购买预览返回的 BUFF 可用资金，并把余额、更新时间及最近一次参考商品、卖单编号和价格保存在本机忽略提交的 `config/buff_balance_cache.json`。这些参考参数只用于发起只读购买预览；该文件不保存 Cookie、Token 或支付密码。

- 仪表盘自动刷新只读取这个本地缓存，不产生 BUFF HTTP 请求。
- 严格余额模式和智能余额模式进行购买预览时会自动更新缓存。
- 余额支付得到明确成功后，界面会先按“原余额减本笔金额”显示付款后估算；后续购买预览再用平台返回值校准。
- 正常候选重试倒计时结束后，程序会在下一轮 SteamDT 拉取前复用缓存中的参考参数，执行一次不自动重试的只读购买预览。充值后的新余额会立即写入缓存；该步骤不查询卖单列表、不锁单、不付款。
- 若尚无完整参考参数，或旧卖单已经失效，自动刷新会跳过或记录警告并继续。真正锁单前仍必须使用当前候选和当前卖单重新预检，旧探针不能直接作为购买许可。
- 如果当前订单只返回带平台错误的 `0.00` 通道，缓存记录这次观察为“不可信”，但不覆盖旧余额。仪表盘显示最近可信值和“本次订单通道未采信”；手动刷新也会明确返回失败，而不是宣称余额已更新为 `0.00`。
- BUFF 请求限流熔断和启动时间窗口的等待结束后不执行这次额外刷新，避免在保护恢复点增加请求。
- 用户点余额卡片的刷新按钮时，后端最多走一个已知商品的卖单查询和一次购买预览，不会调用锁单或支付接口。
- 任务运行时拒绝手动刷新，避免额外请求和真实购买流程并发。
- 无历史参考商品、Cookie 过期、平台验证、请求保护或预览没有返回可识别余额时，保留旧缓存并明确报错，不写成 `0.00`。

### 5.5 当前验收状态

已经通过离线测试：

1. 动态编号 `63/80`都由名称和当前预览字段确认，不按编号猜测。
2. 第一个同名通道为 `0.00` 且不可用、后一个通道为 `7.73` 且可用时，会正确选择后一个通道。
3. 余额不足、不可点击、`real_enough=false`、余额字段缺失或平台报错时不锁单。
4. 锁单网络结果未知时只记录未决订单，不自动重试。
5. 平台订单号在余额付款调用之前写入台账。
6. 付款超时只调用一次，随后进入 `payment_unconfirmed`并阻止继续购买。
7. 平台订单查询明确进入报价阶段时，可以确认付款成功并创建购买记录。
8. 单件价格超过策略上限时，不进入购买预览或锁单。
9. 智能模式在余额足够时复用同一次预览执行余额支付；明确不足时才进入指定手动付款流程。
10. 余额预览状态不明确时，智能模式不锁单、不回退其他支付方式。
11. 余额不足时仍可展示平台明确报告的余额，但不会因此允许锁单。
12. 仪表盘状态轮询只读本地余额缓存；任务运行时手动刷新被拒绝。
13. 正常重试倒计时先完成，再发起恰好一次只读余额预览；非余额支付模式不读取探针、不产生该请求。
14. 带订单级平台错误的 `0.00` 观察不会覆盖最近可信正余额；当前订单仍按不可用处理并禁止锁单。

## 7. 日常判断顺序

1. 看购入价，确认真实现金成本。
2. 看购入市场价和现市场价，判断参考价是否明显变化。
3. 看税后价格，估算 Steam 钱包到账。
4. 看实际折扣比率，判断现金换余额是否划算。
5. 看成交量、卖单深度和冷却时间，不只看低比率。
6. 准备自用时看自用收益。
