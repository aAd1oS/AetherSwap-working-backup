# AetherSwap 双 Agent 协作与审查规范

- 建立日期：2026-08-09
- 适用项目：`D:\Vibe Coding\steam`
- 参与者：用户、Codex、Claude CLI 中接入的 DeepSeek
- 默认方式：Codex 可按用户授权修改；DeepSeek 只读审查，不直接写入工作树

## 1. 结论

这个分工可行，而且适合当前 AetherSwap：项目已经能够真实购买，工作树包含大量尚未提交的本地改进，同时认证、网络、订单和资金逻辑具有较高风险。让第二个模型保持只读，可以获得独立视角并降低部分审查成本，又不会引入两个 Agent 同时编辑同一工作树的冲突。

推荐采用以下结构：

```text
脚本和工具：计算哈希、生成清单、运行测试、搜索文本、输出差异
DeepSeek：读取结果、静态审查、交叉验证、寻找遗漏、整理证据
Codex：需求澄清、架构设计、代码修改、风险裁决、测试设计与最终验收
用户：真实账号、真实交易、外部平台状态和高风险操作的最终批准
```

不建议让两个模型同时修改代码。当前最稳妥的模式是“一个实现者 + 一个只读审查者”。

## 2. 为什么有好处

### 2.1 节省高价模型上下文

文件清单、SHA-256 核对、重复文本搜索、测试输出归类和文档一致性检查，通常不需要复杂架构推理。DeepSeek 可以先完成材料整理，Codex只处理有证据的重点问题。

### 2.2 获得不同模型的独立视角

第二个模型可能发现不同的边界条件、状态竞争、遗漏测试或错误假设。它尤其适合作为“反方审查者”，检查某个修复是否真的覆盖所有调用路径。

### 2.3 建立可复核证据链

只读审查报告要求给出文件、行号、调用链和复现条件。Codex再逐项核对，可以把“模型觉得有问题”变成“当前代码中可以确认或否定的事实”。

### 2.4 降低共享工作树风险

DeepSeek不写文件、不执行真实交易，不会覆盖用户修改，也不会与Codex同时编辑相同模块。所有实际变更仍由一个实现者完成并统一测试。

## 3. 必须承认的限制

### 3.1 上下文同步有成本

两个模型不会天然共享对话。若没有当前快照，DeepSeek容易根据旧报告重复发现已经修复的问题，或者把历史测试数字当成当前结果。

解决办法：每次专项审查先更新 `DeepSeek_接力上下文_2026-08-09.md`，只提供与任务有关的增量信息。

### 3.2 便宜模型不等于安全结论可以降级

DeepSeek的发现必须视为线索，不直接作为资金、认证或网络代码的修改依据。高严重度结论必须由Codex对照当前代码、配置、测试和真实运行条件复核。

### 3.3 哈希不是加密

SHA-256用于完整性校验，不能隐藏Cookie、Token或密码。哈希值应由 `Get-FileHash` 等确定性工具计算，不让任何模型“计算”或猜测。DeepSeek可以检查：

- 是否对正确文件计算；
- 记录值与实际值是否一致；
- 清单是否漏文件；
- 备份是否混入禁止内容。

真正的凭证加密、密钥管理、Windows DPAPI和权限设计仍属于高风险设计，应由Codex负责并经用户批准。

### 3.4 静态审查无法替代真实平台状态

Steam和BUFF接口、限流、Cookie、报价、支付与上架结果具有外部状态。只读模型不能证明真实交易一定成功，也不能仅凭静态代码确定Steam费用字段的最终语义。

## 4. 长期任务分工

| 任务 | 首选执行者 | 最终复核者 | 说明 |
|---|---|---|---|
| SHA-256、文件清单、备份差异 | PowerShell/Git | DeepSeek | 机器计算，模型解释 |
| 文档过期数字、路径和重复内容 | DeepSeek | Codex | 只读、低风险 |
| `rg`搜索、调用点枚举、依赖清单 | DeepSeek | Codex | 必须附命令和证据 |
| 测试失败分类和最小复现建议 | DeepSeek | Codex | 不直接改测试迎合结果 |
| 静态安全审查、边界条件、状态竞争 | DeepSeek | Codex | 报告只是候选发现 |
| 需求拆解、架构、数据模型、状态机 | Codex | Codex + 用户 | 高影响决策 |
| Python/前端/数据库代码修改 | Codex | 测试 + 用户 | 保持单一写入者 |
| Steam/BUFF网络、认证和代理修改 | Codex | 用户批准 + 分阶段测试 | 稳定运行时尽量不碰 |
| 支付、锁单、自动确认、自动上架 | Codex | 用户真实小额验证 | 真实资金风险 |
| Cookie、Token、密钥和账号操作 | 用户 | 用户 | 不交给只读审查模型 |

## 5. DeepSeek适合承担的任务

### 5.1 项目摸底与代码地图

- 枚举目录、入口、模块职责、配置来源和主要数据流。
- 使用 `rg` 列出函数、接口、状态值、配置项和数据库字段的全部调用点。
- 为指定业务绘制从前端、路由、服务、数据库到外部平台的调用链。
- 找出重复实现、废弃路径、未使用模块和文档未覆盖入口。
- 估算一次改动可能影响的文件、测试和用户流程。

### 5.2 静态代码与安全审查

- 检查状态竞争、重复付款、重复锁单、非幂等重试和异常吞噬。
- 检查订单终态复活、非法状态迁移、半写入事务和唯一性缺口。
- 检查Steam报价、库存、`assetid`和本地购买记录是否可能错配。
- 检查自动确认、自动上架是否可能处理不属于当前任务的对象。
- 检查输入校验、金额边界、空值、异常类型和失败关闭行为。
- 检查前端XSS、未转义输出、重复提交、危险按钮和状态误导。
- 检查API或日志是否泄露Cookie、Token、支付链接和代理密码。
- 检查依赖、废弃API、许可证和明显的供应链风险线索。

### 5.3 Diff与修复覆盖审查

- 审查Codex给出的计划、补丁或 `git diff`，寻找回归和遗漏调用点。
- 检查修复是否覆盖正常、异常、重启、并发和中断恢复分支。
- 检查新保护是否能被旧兼容路径、自定义策略或配置覆盖绕过。
- 比较修改前后行为，指出哪些变化是有意的、哪些可能是副作用。
- 提出反例和攻击路径，但不执行真实攻击或规避平台限制。

### 5.4 测试设计与结果分析

- 生成边界值、重复操作、并发、中断恢复、网络异常和状态迁移测试矩阵。
- 检查现有测试是否真正断言业务结果，而不是只断言函数被调用。
- 对Pytest失败进行聚类，定位共同根因和最小复现方向。
- 对Mock范围、测试隔离、临时数据库和网络请求替身进行审查。
- 对测试通过后的残余风险作说明，不把单元测试等同于真实交易安全。
- 在只读限制允许时运行无缓存测试；权限不足时只给出命令，不绕过限制。

### 5.5 日志与故障分析

- 将长日志整理成时间线、失败阶段、重试次数和最终状态。
- 对比两次运行日志，找出网络、认证、候选筛选和订单行为变化。
- 区分429、401、10054、超时、Cookie过期、平台拒绝和本地逻辑错误。
- 统计重复错误和首个根因，避免被后续连锁警告误导。
- 检查日志脱敏情况；用户提供的日志如含秘密应停止引用具体值。

### 5.6 文档与接力维护

- 找出过期测试数字、备份路径、日期、命令和功能说明。
- 比较多份文档，标出重复内容、互相冲突的结论和可合并章节。
- 将专项审查压缩成高优先级清单、小白说明或下一轮任务单草案。
- 检查代码、界面文案、配置默认值和文档描述是否一致。
- 更新建议只以报告形式交给Codex，不直接编辑文档。

### 5.7 备份、Git与发布核对

- 复核安全源码树文件清单和当前工作树的差异。
- 检查备份是否混入账号配置、数据库、日志、浏览器资料和虚拟环境。
- 复核 `Get-FileHash` 生成的SHA-256是否与记录一致。
- 分析 `git status`、`git diff`和暂存范围，指出不应提交的文件。
- 检查发布说明、启动脚本、依赖清单和回滚说明是否完整。
- 哈希、清单和Diff必须由工具产生，DeepSeek只解释与复核。

### 5.8 方案反方与决策辅助

- 对Codex方案提出失败场景、替代方案和取舍问题。
- 评估简单修复与完整重构的影响范围、测试成本和回滚难度。
- 区分“当前配置不可达”“潜在缺陷”“已确认问题”和“真实样例待验证”。
- 对是否值得实施、是否应等待真实样例给出只读建议。
- 最终架构选择、严重度和实施决定仍由Codex与用户完成。

### 5.9 适合日常反复委派的小任务

1. 阅读一份新日志并生成短时间线。
2. 比较两份日志、报告、配置模板或备份清单。
3. 枚举一个函数或状态的全部调用点。
4. 审查一个小Diff和对应测试是否匹配。
5. 为一个Bug列出最小复现与测试矩阵。
6. 检查文档是否仍引用旧路径、旧数字或已删除功能。
7. 检查新日志或API字段是否可能泄露秘密。
8. 将长报告压缩成需要Codex复核的前五项。
9. 为下一次专项审查生成只读任务单草案。
10. 在没有发现问题时明确报告“当前范围未发现可确认缺陷”。

## 6. DeepSeek不应承担的任务

- 不写入、格式化或批量重排当前工作树。
- 不执行 `git reset`、`git clean`、`git checkout --`、删除或移动文件。
- 不读取或输出 `config/credentials.json`、Cookie、Token、`.maFile`、数据库和浏览器资料。
- 不登录Steam、BUFF、GitHub，不接受报价，不锁单，不付款，不上架。
- 不修改Steam/BUFF网络路由、代理、限流和认证逻辑。
- 不根据旧报告直接宣布当前存在P0漏洞。
- 不把测试通过等同于真实交易安全。
- 不把SHA-256描述成加密或秘密保护。

## 7. 标准协作流程

### 第一步：Codex准备任务单

任务单必须写明：

- 当前项目路径和日期；
- 审查范围与明确排除范围；
- 当前已知行为和最近测试结果；
- DeepSeek只读限制；
- 期望报告格式；
- 禁止访问的敏感路径。

### 第二步：DeepSeek只读审查

每条发现必须包含：

```text
编号与严重度
置信度
文件与行号
触发条件
代码证据或命令输出
实际影响
最小复现或建议测试
建议方向（不直接改代码）
```

无法确认时必须写“待验证”，不能用确定语气补全未知事实。

### 第三步：Codex复核

Codex逐项给出：确认、部分确认、当前不触发、证据不足或误报，并说明修复难度、影响范围和是否需要真实样例。

### 第四步：用户决定实施范围

真实资金、认证、网络和自动出售相关修改，先由用户确认。低风险本地校验和测试补充可以按用户授权直接实施。

### 第五步：Codex实现与验证

保持增量修改，先跑针对性测试，再跑完整测试。不得为了让报告“全部通过”而降低现有安全保护。

### 第六步：回写状态

更新当前接力文档、正式说明和安全备份。旧审查报告保留原始证据，但在顶部注明实施和复核状态。

## 8. 冲突裁决规则

当两个模型结论不一致时，按以下优先级处理：

1. 当前工作树中的实际代码和可重复运行结果；
2. 当前配置下真实可达的调用链；
3. 官方接口语义或真实低风险样例；
4. 当前维护文档；
5. 模型推断和历史报告。

任何模型都不能凭“看起来像”直接修改资金或认证逻辑。

## 9. 成本控制建议

- 给DeepSeek单一专项，不要一次要求审查整个项目。
- 优先让脚本生成清单，再让模型读清单，不让模型逐文件漫游。
- 已确认无问题的模块不要重复审查，除非调用链发生变化。
- DeepSeek报告控制在高信号发现，明确写“未发现问题”也有价值。
- Codex只读取DeepSeek报告及必要证据，不重复无目的全库扫描。

## 10. 当前采用的长期决策

1. DeepSeek继续保持只读。
2. Codex是唯一代码实现者和最终技术裁决者。
3. 用户保留真实平台操作和高风险修改批准权。
4. 确定性校验优先交给脚本，DeepSeek负责复核结果。
5. 每次专项任务使用接力文档同步进度，不依赖模型记住历史对话。
6. 网络、支付、认证和自动出售不因节省Token而降低复核标准。
7. Claude CLI通用启动Prompt维护在 `docs/DeepSeek_CLI主Prompt.md`。
