# 交付、维护与审查

本文给维护者使用。同学首次安装只需阅读 01、02、04，遇到问题再看 03。

- 2026-09-27 核查时远程最新提交为 `9776ff5a787db858d76c6ebad47b115fb22fced8`，提交日期 2026-08-14，尚无 GitHub Release。

详细对比和测试记录见 [2026-09-27 交付审查](archive/2026-09-27_同学交付审查.md)。

## 2. 源码交付与个人备份分开

交付只包含程序、静态资源、测试、安装文件和文档。不要直接压缩整个工作目录，不要使用完整配置导出作为同学的初始化文件，也不要用“出厂重置”清洗自己的业务现场。

| 可以交付 | 不得随源码交付 |
|---|---|
| app、analysis、buff、steam、steamdt、utils 中的源码 | 个人账号、Cookie、令牌、代理凭据、通知地址 |
| web、flags 中的运行资源 | PRIVATE INF、浏览器用户资料、.maFile |
| config/__init__.py、经检查为空目标的 config/config.json | config 其他 JSON、数据库、备份、缓存 |
| tests 的有效测试源码 | .venv、.playwright、日志、.env、.agreed_disclaimer |
| run.py、requirements、启动器、LICENSE、当前文档 | .git、助手会话目录、个人快捷方式、旧文件 .orig/.bak |
| 两个有文档入口的只读诊断脚本及启动器 | 历史模拟结果、诊断原始响应、生成卡片和私人截图 |

`config/strategies.json` 也不默认交付：自定义策略和维护者当前配置不是同学的初始设置。需要分享策略时，另行导出并人工审查，不连同完整配置导出。系统内置策略仍来自源码。

本次补充的 .gitignore 是防误提交措施，**不保护已经追踪的文件，也不能证明旧提交历史没有敏感信息**。不要用 `git add .` 或 `git add -A` 把真实工作目录全部打包。Docker 构建上下文是另一套排除规则；本次不验收原有 Docker 部署。

## 3. 上传流程

推荐使用此次审核的干净源码包，或按同样白名单生成新快照。后续再改代码时必须重建快照，不能重复上传过期包。

1. 确认目标仍是自己的**私有**仓库，确认账号有访问权。
2. 在独立的发布目录克隆自己的仓库，**不要覆盖实际运行目录**。
3. 对比干净快照与发布目录：替换修改文件、加入新增文件；在发布目录删除新版已合并/废弃的旧文档。不要仅拖入新文档而留下两套教程。
4. 特别移除旧版 `docs/hosts-backup-20260811.txt`、旧双模型 Prompt 和旧安装/数据安全说明；以新版文档导航为准。保留 LICENSE。
5. 核对将提交的文件名和差异，排除个人数据；不能把“仓库私有”当作允许上传秘密。
6. 在发布目录进行干净测试，检查首页文档、启动器和源码都有提交。
7. 人工确认后再 commit、push 到自己的 `main`。不要强制推送，不改原作者仓库。
8. 上传完成后从 GitHub 核对新提交，再以新目录克隆验收，确认不是仍在运行本机旧目录。
9. 在 GitHub 仓库设置中邀请同学为协作者；让其接受邀请，并提供仓库链接与确切提交号。当前并未代为邀请。

旧 `upload-safe-backup-to-github.ps1` 会从维护者固定备份目录选择快照，并在独立上传目录准备替换文件；它**不会自动从当前项目生成最新快照**。本次不以该脚本为交付入口，不应不看快照日期就双击上传。

以上涉及删除的步骤仅针对独立发布目录中明确废弃的源码/文档，不能对运行目录或整个磁盘执行清理。也不要删除 .git 来冒充干净升级。

## 4. 同学更新时

1. 停止购买，核对未决平台订单，并完整退出后台。
2. 将自己的 `config/` 和必要日志私下备份到仓库外；其中包含凭据，不能发给维护者。
3. 在自己的克隆目录检查 `git status --short`，有本地源码修改先停止更新并沟通，不用 reset --hard。
4. 无源码冲突时执行 `git pull --ff-only`，再使用 .venv 安装当前 requirements、运行 pip check。
5. 启动后核对当前账号、持仓、订单和策略授权，再恢复业务。不要导入维护者配置。
6. 数据库迁移后不保证只回退代码就能恢复；回退需配套一致的私人数据备份。

同学不需要同步维护者的交易数据库。首次使用空数据库，后续更新保留自己的数据库。

## 5. 验收方法

不要在存有真实凭据的业务目录中盲目运行测试。使用不含 config 运行数据、浏览器会话和 .env 的临时源码副本：

```powershell
# 在干净副本中，先按安装说明创建 .venv 并安装 requirements.txt
.\.venv\Scripts\python.exe -m pip install pytest
$env:PYTHONDONTWRITEBYTECODE = "1"
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider
.\.venv\Scripts\python.exe -m pip check
```

可选前端语法检查（维护者需要 Node.js，普通使用者不需要）：

```powershell
Get-ChildItem web/js -Filter *.js | ForEach-Object {
    node --check $_.FullName
    if ($LASTEXITCODE -ne 0) { throw "JavaScript syntax check failed" }
}
```

至少核对：没有凭据也能安装并打开空页面；缺账号不能启动真实购买；默认自动扣款/出售/确认不启用；停止和完整退出分开说明；所有本地文档链接有效。测试通过不能代替真实平台验收。

本次复用已有 Python 3.11.5 环境验收代码，没有声称在另一台全新 Windows 上重新下载全部依赖或完成真实支付、收货、上架。依赖没有锁定全版本，后续变更需重验。
